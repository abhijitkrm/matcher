not committed — regenerate with the commands below.

## Ladder rescan fix @ 2026-10-09

W3 run for 1M ops instead of 100k (`vectorgen --workload w3 --n 1000000`)
cancels faster than it adds, so the book drains to a handful of orders.
Each time a side's last level emptied, the top-of-book rescan walked the
occupancy bitmap word by word to the end of the 1M-tick ladder (about
7,800 words) before returning "empty"; a profile put 98% of the time
there. Every port now keeps a summary bitmap (one bit per non-empty
bitmap word) and sets the cursor straight to empty when the side's count
reaches zero. Output is unchanged (golden vectors and bench checksums);
each port gained a randomized test of the cursor against a sorted set.

| impl | W3-drain before | W3-drain after | W3 (100k) / W2 / W4 |
|---|---|---|---|
| rust (8657dc7) | 0.60M | 13.0M | unchanged (A/B) |
| cpp (55091ea) | 0.64M | 15.3M | unchanged (A/B) |
| go (81542be) | 0.36M | 7.2M | unchanged (A/B) |
| java (20e563b) | ~1.2M | ~5M | unchanged (A/B) |
| ts (223341e) | 0.30M | 4.8M | unchanged (A/B) |

Apple M1, ops/s, single book. The default W3 (100k ops) never drained the
book, which is why the earlier tables did not show this.

- No workload collapses at 10M ops any more: before the ladder rescan fix,
  drained W3 ran at 0.3–1.2M ops/s.

  port. The book no longer fits in cache, the same memory-bound curve as W5
  at smaller sizes.

- This sweep is what found matcher-ts's bench could not load a corpus over
  ~512 MB (V8's maximum string length); fixed in matcher-ts e7986ae.

## Reading it

- **C++ ≈ Rust** (within noise): 10–23M ops/s, p50 ≈ 41–42ns (measurement floor).
- **Go ~2–4× slower**: 2–9M ops/s — GC write barriers + `map` overhead; still
  respectable. GOGC variants not shown (default).
- **Depth curve (w5)** shows the expected memory-bound behavior: a 1k-order
  book is cache-resident (~20M ops/s); a 1M-order book spills to DRAM
  (~4M ops/s). This is the honest physics of order books — dense local books
  are fast; huge sparse books are memory-latency-bound.
- **Java** matches native-tier throughput once JIT-warm (12.5M ops/s on the
  sweep) but its max column shows occasional JIT/GC stalls — expected on a
  short unpinned run.
- **TypeScript (V8)** lands near Go's ballpark (~4–5.5M ops/s): per-command
  allocation in the harness and GC keep the tail heavier than the median.
- Max column reflects occasional page faults / TLB misses / scheduler noise on
  an unpinned macOS process.

## Per-language notes

- **rust**: pool slab + intrusive levels + bitmap ladder w/ top-of-book cursor
  + open-addr map (xor-fold hashing). All allocation at construction.
- **go**: same structures; `map[uint64]uint32` for ids (Swiss-table maps since
  Go 1.24 are genuinely good); sorted-slice tree index. GC pauses visible in
  p99.9+ columns.
- **cpp**: same structures; `std::map` tree fallback; template-dispatched sink
  (zero-overhead).
- **ts**: same structures on flat typed arrays (`Float64Array`/`Int32Array`
  pools, 32-bit bitmap words); sorted-keys `Map` tree fallback.
- **java**: same structures on flat `long[]`/`int[]` pools; `TreeMap` fallback;
  `@FunctionalInterface` sink. Numbers are JIT-warm.

## rust chunk layout + apply_batch, and aggregate (shard-per-core) @ 2026-10-27

matcher-rust (Unreleased: LAYOUT.md chunk store, tagged `OrderMap`,
`apply_batch`) on the same machine and corpora as the cpp section above.
Apple M1, 4 P + 4 E cores, best of 5 reps, ops/s. Single-core rows use
`--mode throughput`; aggregate rows use `--mode scale` (BENCH.md §2.1:
8 threads, each with its own book and symbol partition, no shared state;
total = 8 × ops / slowest thread). Rust numbers are for
`--features prefetch` with `-C target-cpu=native`; the default build
(no `unsafe`, no prefetch) differs only on W4 (23.6M) and W5 1M (9.4M).

| workload | rust, 1 core | rust, 8 shards | cpp, 1 core | cpp, 8 shards |
|---|---|---|---|---|
| W1 build 1M | 37.7M | 56.2M | 37.2M | 63.4M |
| W2 sweep | 27.9M | 78.8M | 25.5M | 78.1M |
| W3 churn | 23.2M | 65.7M | 23.0M | 68.4M |
| W4 mixed | 40.5M | **109.8M** | 39.7M | **112.5M** |
| W5 1k live | **94.0M** | 284.2M | **91.5M** | 304.5M |
| W5 100k live | 24.6M | 75.3M | 23.2M | 68.2M |
| W5 1M live | 13.3M | 39.2M | 13.1M | 40.1M |

- **Single-core and aggregate are different claims.** Single-core is the
  engine's speed on one book. Aggregate is what a shard-per-core
  deployment sustains; it is not 8× because the 4 E-cores are slower
  and the shared L2/memory bandwidth saturates (W5 1M: 13M per core
  alone, 4.6M per thread at 8 threads).
- The realistic mixed workload (W4) crosses 100M ops/s only as an
  aggregate: 110M (rust) and 112M (cpp) on 8 shards. On one core it is
  40M, limited by cache misses on a 100k-order book, not by the code.
- Single-core above 100M was not reached: the best case (W5 1k live,
  everything cache-resident) is 94M. Always-on prefetch for books under
  64k live orders was tried and is far worse (62M), so the threshold in
  LAYOUT.md §4 stays.
- Noise: the machine runs other apps; individual runs of W5 1k vary
  87–95M. Compare builds with interleaved A/B rounds, not single runs.

## java chunk layout + applyBatch + aggregate @ 2026-10-28

matcher-java (Unreleased: LAYOUT.md chunk store on flat `long[]`, tagged
`OrderMap`, `applyBatch`) on the same machine and corpora. JDK 20, Apple M1,
`-Xms2g -Xmx4g -XX:+UseParallelGC` (`-Xms4g -Xmx8g` for scale), best of 15
reps (JIT-warm), ops/s. Throughput = `--mode throughput`; 8 shards =
`--mode scale`.

| workload | java, 1 core | java, 8 shards | rust, 1 core | cpp, 1 core |
|---|---|---|---|---|
| W1 build 1M | 27.5M | 47.4M | 37.7M | 37.2M |
| W2 sweep | 24.0M | 78.7M | 27.9M | 25.5M |
| W3 churn | 18.5M | 32.8M | 23.2M | 23.0M |
| W4 mixed | 29.4M | 57.5M | 40.5M | 39.7M |
| W5 1k live | 69.1M | 250.0M | 94.0M | 91.5M |
| W5 100k live | 19.1M | 41.2M | 24.6M | 23.2M |
| W5 1M live | 6.2M | 21.4M | 13.3M | 13.1M |

- **The look-ahead pipeline is off by default in Java** (LAYOUT.md §4 allows
  skipping it). Java has no non-blocking prefetch, so the pipeline's plain
  loads stall retirement. With it on, W4 ran at 12.8M and with it off at
  27.9M (2.2x); W3 +62%, W5 100k +54%, W5 1M +6%.
  `setPrefetchThreshold(n)` re-enables it; the golden suite forces it on.
- **`CommandBatch`**: a struct-of-arrays batch (`applyBatch(CommandBatch, …)`)
  with a byte opcode instead of `Command` objects and `instanceof` dispatch.
  Same events (golden suite checks it against `apply` for every vector);
  +3-7% over the `Command[]` path. The bench uses it unless `-Dbatch=obj`.
- ParallelGC over the default G1: +17% on W4 (12.9M → 15.1M, before the
  two changes above; cause not investigated). `-XX:-TieredCompilation`, raised inline limits and
  `LoopUnrollLimit=0` were all neutral or worse.
- Java reaches about 72-74% of native single-core on W4 and W5 1k. The
  rest is bounds checks and no prefetch; no single hot spot was found.
- Correctness: golden suite (including `applyBatch` and `CommandBatch` vs
  `apply`), snapshot and ladder tests pass; `diffuzz.sh` is 5-way identical
  on seeds 1-8.

## go chunk layout + ApplyBatch + aggregate @ 2026-10-28

matcher-go (Unreleased: LAYOUT.md chunk store, tagged `omap`, `ApplyBatch`,
PGO profile for `matcherbench`) on the same machine and corpora. Go 1.27,
Apple M1, best of 15 reps, ops/s. Throughput = `--mode throughput`; 8 shards
= `--mode scale`.

| workload | go, 1 core | go, 8 shards | java, 1 core | rust, 1 core |
|---|---|---|---|---|
| W1 build 1M | 28.7M | 49.4M | 27.5M | 37.7M |
| W2 sweep | 22.9M | 77.1M | 24.0M | 27.9M |
| W3 churn | 18.6M | 39.8M | 18.5M | 23.2M |
| W4 mixed | 26.0M | 61.1M | 29.4M | 40.5M |
| W5 1k live | 60.9M | 222.7M | 69.1M | 94.0M |
| W5 100k live | 17.5M | 41.1M | 19.1M | 24.6M |
| W5 1M live | 7.9M | 26.1M | 6.2M | 13.3M |

- **Look-ahead threshold raised from 64k to 256k live orders in Go.** Go has
  no prefetch intrinsic either, so the pipeline's plain loads cost on books
  that still mostly hit L2. A/B on W4 (about 100k live): 19.0M with the
  pipeline, 26.7M without. On the 1M-order book it wins: 7.9M vs 6.1M.
  Thresholds 2^17-2^19 all keep both results; 2^18 is used. The pipeline is
  on only for the dMap + dChunk stages. `-tags matcher_noprefetch` turns it
  off for comparison. (This lifted W2 as well, 18.9M → 22.9M.)
- **PGO**: `cmd/matcherbench/default.pgo` is worth about +7% (W5 1k 56.7M →
  60.8M). It lets the compiler inline the `priceIndex` wrappers and ladder
  calls at hot sites; without PGO they exceed the inliner's budget of 80
  (cost 117-129). A profile regenerated from the new code was no better.
- Bounds-check elimination (`-gcflags=-B`) and `GOGC=off` changed nothing,
  so neither bounds checks nor the GC is the limit.
- Go is at about 65% of Rust on a cache-resident book (W5 1k) and 59% on
  the 1M-order book; the rest is codegen (register allocation, no
  non-blocking prefetch). Not chased further.
- Compiler knobs tried and discarded (all within +-1% over three interleaved
  rounds): `-d=pgoinlinecdfthreshold=100`, `-d=pgoinlinebudget=6000`,
  `GOEXPERIMENT=newinliner` (alone and with `inlbudgetslack=200`),
  `-d=alignhot=1`, `-gcflags=-l=4`.
- Correctness: golden vectors, `ApplyBatch` vs `Apply` on a 300k-order book
  (the test fails if the pipeline is not engaged), snapshot and ladder
  tests pass; `diffuzz.sh` is 5-way identical on seeds 1-8.

| FPGA, UC Irvine student project ([page](https://projects.eng.uci.edu/projects/2025-2026/high-frequency-trading-project)) | 75M orders/s | self-reported, unaudited | FPGA | not comparable |
| FPGA, Algo-Logic ([STAC 2013](https://stacresearch.com/system/files/resource/files/STAC%20Summit%20-%204%20November%202013%20-%20Algo-Logic.pdf)) | 150M searches/s | order-book lookups, not full matching | FPGA | not comparable |

What this does and does not show:

- **On a small cache-resident book our no-op-sink number (115M W5 1k, Rust) is
  above every *published, reproducible* software figure we found** (LMAX 6M,
  exchange-core 5-6M, the best public engine in the harness 9.25M) and above
  the 32M in the paper text. It is **not** above the vendor's own claim:
  FlashOne is listed at 103.39M msgs/s in the harness README. That engine is
  proprietary, the figure is self-reported, and it is measured with report
  emission included, which our no-op sink excludes, so the two are not yet
  comparable. On the mixed workload with a ~100k-order standing book our lead
  over the paper's 32M is 1.4x, not an order of magnitude. The preprint itself
  shows the same dependence on cache residency (10,000 symbols per core: 31% of
  its single-symbol rate; a standing book about -10%), so book size and symbol
  count matter more than the ratio.
- **The large ratios against LMAX and exchange-core are mostly hardware and
  era** (2010-2011 Xeon vs a 2020 M1) and, for LMAX, a business-logic
  processor that did more than match. They are not evidence that our algorithm
  is 7x better.
- **Disruptor and Aeron are not matching algorithms.** Their figures are
  transport and consensus rates and have no matching-engine equivalent here.
  A real deployment of our core would sit behind such a layer and would be
  bounded by it (Aeron Cluster: hundreds of thousands to low millions of
  messages/s per replicated stream).
- **Not shown:** latency under load, behavior with persistence or replication
  switched on, or any head-to-head run. The preprint's authors publish a
  benchmark harness and reference hashes
  ([flash1-dev/matching-engine-benchmark](https://github.com/flash1-dev/matching-engine-benchmark),
  MIT). Their unit, a "message", is an inbound new/cancel/modify command (about
  2 per new order), the same unit as our ops/s, but their mix is cancel-heavy and
  our W4 is 82% replace, and their timed region includes a 64-byte report per
  result over an inter-thread queue. Running our ports through that harness on
  one machine is the only comparison that would be a fair "faster than" claim.
  It requires Linux (GCC 14+, Boost) and a C-ABI adapter that maps our events
  onto their six report types. We built the adapters and ran it: see
  "Third-party harness" below. Result in one line: level with the best public
  engine (+2% on the default transport, +7% on a shared batched one, worst case)
  and about a fifth of the vendor's own 103M.

## Third-party harness (flash1-dev/matching-engine-benchmark) @ 2026-10-28

The harness from the Flash One preprint
([repo](https://github.com/flash1-dev/matching-engine-benchmark), MIT) run on
this machine with our C-ABI adapters (`tools/meb-adapters/`). It replays ~2.0M
new/cancel/modify messages (power-law depth, 95% cancel, 20% modify, 15% IOC),
requires a **byte-identical report stream** (SHA-256 against a consensus first
established from Liquibook, QuantCup and Exchange-core), audits book state at
random points, and **includes in the timed window**: the ABI call per message,
a 64-byte report per result pushed through an inter-thread queue, and a
drainer thread that records every report. Apple M1 in a 4-CPU Docker (arm64
Linux, GCC 14.2) VM, so absolute numbers are not comparable with the
Graviton4 numbers in their README; only engines run side by side here are.
Median of 10 runs, M msgs/s, every cell VALID (hash PASS, audit PASS).

Each engine is run twice: on the **harness's default transport** (one atomic
publish per report) and on a **batched ring** that publishes every 32 reports
(`engine_get_transport` + `flush()`, allowed by the harness). The same ring
(`ring_transport.hpp`) is used for all three engines, including lcv3 via a
shim, so the columns compare engines, not transports.

| scenario | lcv3 | matcher-cpp | matcher-rust | lcv3, ring | matcher-cpp, ring | matcher-rust, ring |
|---|---:|---:|---:|---:|---:|---:|
| static | 13.84 | 13.58 | 12.95 | 24.57 | 24.52 | 24.12 |
| normal | 11.90 | 13.09 | 12.04 | 19.62 | 22.83 | 22.40 |
| swing-25 | 12.15 | 12.90 | 11.85 | 18.56 | 22.11 | 21.60 |
| swing-40 | 12.16 | 12.65 | 11.68 | 19.88 | 22.07 | 21.08 |
| flash-crash | 12.15 | 12.67 | 11.47 | 20.28 | 21.60 | 20.61 |
| **worst case** | **11.90** | **12.65** | **11.47** | **18.56** | **21.60** | **20.61** |

(Second full run, after the forced-inlining change to matcher-cpp and
matcher-rust; lcv3 is unchanged. The first run, before it, had worst cases of
lcv3 11.99 / 19.33, matcher-cpp 12.18 / 20.62, matcher-rust 10.61 / 17.76.)

Their other two baselines, same machine (separate session): Liquibook 6.0 on
`normal` and 0.035 on `static`; QuantCup 5.3 on `normal`, 0.16-0.51 on the three
volatile scenarios, and INVALID on `static` and `normal` (its depth query
trips the anti-cheat limit on time spent in `engine_query_*`).

What this shows:

- **matcher-cpp is modestly ahead of the best public engine, matcher-rust is
  level with it:** worst case, matcher-cpp is +6% on the default transport
  (12.65 vs 11.90) and +16% on the shared ring (21.60 vs 18.56); matcher-rust
  is 4% behind on the default transport (11.47) and 11% ahead on the ring
  (20.61). lcv3 wins `static` on the default transport; matcher-cpp wins the
  other four by 4-17%. All three are conformant and 2-80x ahead of Liquibook
  and QuantCup. The 115M no-op-sink figure above does not carry over: this
  harness is dominated by report emission.
- **The transport matters more than the engine.** Moving every engine from the
  default transport to the batched ring adds 56-80% (lcv3 11.90 -> 18.56,
  matcher-cpp 12.65 -> 21.60, matcher-rust 11.47 -> 20.61). With every report
  discarded (a measurement-only build; its hash fails by construction)
  matcher-cpp runs at 40.7M msgs/s on `normal`, i.e. the matcher plus ABI call
  is ~25 ns/msg, in line with our 40M on W4. The rest is writing 64 bytes per
  report, the 1M-report queue the harness requests, and the drainer thread.
- **The batched transport is a different design point, not a free win.**
  Reports reach the consumer up to 31 reports late. The harness measures
  throughput only and explicitly allows it, but a venue that needs per-message
  publication would not run it. Compare engines within a column.
- **The vendor's claim stands unreproduced.** FlashOne is listed at 103.39M
  msgs/s in the same harness (Graviton4/EPYC, a proprietary engine, with
  whatever transport it ships). Our best here is 20.6M, about a fifth of that.
  Whether the gap is the matcher, the transport or the hardware cannot be told
  from this data; the discard build shows our matcher side alone is ~40M on
  this workload.
- Not done / caveats: a cache-resident (4096-slot) ring measured 25.7M but
  violates the harness's "room for at least `capacity`" contract, so it is not
  reported as a result and is not in the saved adapter. The lcv3 shim reaches
  the ring through the harness's function-pointer vtable, while the matcher-cpp
  adapter calls the ring inline, which slightly favors matcher-cpp in the ring
  column. Go, Java and TypeScript were not run (cgo/JNI/no practical C-ABI
  path, and the batch entry point was not implemented).

## Single-core experiments that did not pay off @ 2026-10-28

Tried while chasing 100M ops/s on one core (W5 1k live, C++/Rust 91-94M at the time). None
is in the code; recorded so they are not repeated. Quiet machine, interleaved
A/B, three rounds each.

- **Order-id block locality hash** (C++): home slot = hash(id >> 6) + (id & 63),
  so 64 consecutive ids share a contiguous run and dense ids touch few cache
  lines. Correct (golden suite passes), but much slower on churn-heavy
  workloads: W1 32.4M -> 19.8M, W2 24.4M -> 13.9M, W3 21.5M -> 12.8M, W5 1M
  12.6M -> 6.1M, no gain on W5 1k or W4. The 64-slot runs lengthen linear-probe
  chains at 50% load.
- **Right-sized `max_orders`** (the W5 1k corpus header asks for 201k, so the
  map has ~512k slots for ~1,000 live orders): C++ 87.6M -> 91.1M (+4%), Java
  +2-4% (inside its noise). The map footprint is not the main cost;
  `OrderMap.find` looks hot in a Java profile (30-36% of timed samples) mostly
  because it is the first dependent cache access of every command.
- **Profiles are flat** in all five languages: no function above ~20% of the
  timed work, so there is no single hot spot left to remove. Remaining cost is
  spread over ~8 loads and 60-80 instructions per replace (~34 cycles).
- Per-language flags/structure that also did not help are listed in each
  port's section above (Go compiler flags, TS struct-of-arrays, Java look-ahead).
- Single-core 100M ops/s was not reached by any of the above. It was reached
  afterwards by forcing the hot path inline in Rust and C++ (next section).

## Forced inlining in Rust and C++ @ 2026-10-28

Found while asking why the Rust harness adapter was 15-25% behind C++ with
reports discarded (29M vs 39M msgs/s): callgrind showed ~350 instructions per
message in the Rust adapter against ~246 in C++. LLVM kept `apply`,
`unlink_level`, `cross`, `Store::push/unlink` and `OrderMap::remove` out of
line even with `#[inline]` and fat LTO, so each message paid call, argument-copy
and bounds-check overhead that g++ had already inlined away. In C++ the same
helpers were implicitly inline but not forced. Both ports now mark the hot path
`#[inline(always)]` / `[[gnu::always_inline]]`: `apply`, `new_order`, `cancel`,
`replace`, `rest`, `cross`, `emit`, `reject` and the store, order-map and
price-index operations.

Interleaved A/B on a quiet machine (3-4 rounds, `--mode throughput`, best of 9),
M ops/s, before -> after. The Rust column is the first step (the helpers and
`apply`); the second step (the top-level functions) took W5 1k to 115M and W4 to
45.5M:

| workload | Rust | C++ |
|---|---|---|
| W2 sweep | 27.3 -> 30.4 (+11%) | 23.9 -> 25.6 (+7%) |
| W3 churn | 22.9 -> 24.5 (+7%) | 21.2 -> 23.7 (+12%) |
| W4 mixed | 39.8 -> 42.7 (+7%) | 38.5 -> 43.2 (+12%) |
| W5 1k live | 92.6 -> 98.9 (+7%), 115 with the remaining helpers | 86.7 -> 101.2 (+17%) |
| W5 100k live | 24.0 -> 25.8 (+7%) | 21.8 -> 24.9 (+14%) |
| W5 1M live | 13.1 -> 13.9 (+6%) | 12.4 -> 14.0 (+13%) |

Final numbers (best of 15): Rust W5 1k 115.3M (prefetch + native) and 115.8M
(default build: safe code only, no native flags); C++ W5 1k 105.5M. W4 46.0M and
43.9M; 8-shard W4 aggregate 119.7M for both. Rust gained more because it had
more left out of line (apply, new_order, cancel, replace and rest as well as
the helpers); the 115M figure comes from that second step (forcing the
top-level functions on top of the helpers: 99M -> 115M on W5 1k).

Checks: all tests, the 5-way differential fuzz (seeds 1-8) and the harness
report-stream hash (VALID) pass for both. In the harness, instructions per
message in the Rust adapter fell 350 -> 296 and its default-transport
throughput rose ~9-10.8M -> ~11.1-11.5M (ring 18.2M -> 21.0M); C++ rose
~12.3M -> ~13.2M (ring ~22M -> 22.5M).

Not done: Java, Go and TypeScript cannot force inlining (the JIT / Go inliner
decide); the Go compiler flags that raise the budget were measured neutral.

## Latency @ 2026-10-28

Per-command latency of the matching core: single-threaded replay of a corpus,
no-op event sink, one timed `apply()` per command (`--mode latency`, BENCH.md
section 2), ns, median of 3 runs per column. Apple M1, same builds as the
throughput tables. No network, journal or report emission is included.

**How to read it.** The M1's 24 MHz timer ticks every 41.7 ns, so every
percentile is a multiple of that and a p50 of 0 or 41-42 means "within one
tick", not a precise median. The *mean* in this mode also includes the cost of
the two timer reads (~12 ns here), so it overstates the engine. The best central
figure is therefore the mean per command from throughput mode, where no timer
is in the loop (first table). `max` is dominated by the machine (interrupts,
scheduling) and, for Java and TypeScript, GC and JIT; it is reported but is not
an engine property.

## Go and Java restructuring toward 100M @ 2026-10-28

Goal: take Go and Java from 61-69M to 100M ops/s on W5 1k. Neither got there.

**Go: 60.8M -> 67.8M (+11%) on W5 1k.** Kept (interleaved A/B, 3 rounds, M ops/s):

| workload | before | after |
|---|---:|---:|
| W3 churn | 18.8 | 20.4 |
| W4 mixed | 26.5 | 30.0 |
| W5 1k live | 60.8 | 67.8 |
| W5 100k live | 18.3 | 20.6 |
| W5 1M live | 7.3 | 8.7 |

- A `replace` is ~8 real calls in Go (`apply`, `levelMut`, `store.unlink`,
  `unlinkLevel`, `cross`, `levelInsert`, `store.push`, the sink), and Go's ABI
  has no callee-saved registers, so each call spills and reloads. `replace` now
  has a ladder fast path with all of that written out by hand (+ a guard that
  skips `cross` unless the opposite best is marketable); the tree index keeps
  the generic code. The gain is concentrated on the larger books (W5 1M +16%,
  100k +10%) and is small on W5 1k (+1-2%).
- Building events directly in the book's reused `Event` instead of passing a
  56-byte struct by value and copying it: W5 1k +7%, W2 +5%.
- A PGO profile regenerated from the final code with long runs: +5% on W5 1k,
  +4% on W4 (a profile from the older code and short runs had been neutral).

Tried and dropped (Go): caching slice headers in locals and a fixed-length chunk
slice (0%); a one-load order-map look-ahead on small books, with a call (-25%)
and written inline (0 to -3% on W5 1k, +1-3% on W3/W4/100k); Go compiler flags
(earlier section). Ceiling check: skipping the sink call entirely (throwaway
build) only reaches 76M on W5 1k, so the interface dispatch is ~2 ns of the
~15 ns per command; the other ~13 ns is the core itself, against ~8.7 ns for
Rust. A `pprof -disasm` of `replace` puts the single hottest instruction at the
order-map tag compare (~20% of the function), a dependent-load stall that the
look-ahead did not remove.

**Java: no change kept.** Ceilings and levers measured on W5 1k (baseline 67M):
- skipping the sink call entirely: 71M (+6%), so the sink/event path is not
  the issue;
- HotSpot `-XX:CompileCommand=inline,...` on the top-level methods: +2% on
  W5 1k, -10% on W3/W4; on the whole package it collapsed W5 1k to ~24M;
- the order map on raw memory via `sun.misc.Unsafe` (no bounds checks or array
  headers), same algorithm: W5 1k +3%, W4 +5%, W3 +12%, W5 100k +4%. Not adopted:
  it would need Unsafe throughout, which newer JDKs are deprecating, and
  converting every structure would plausibly reach the high 70s, not 100M.
- Raw-memory `find` is also where a JFR profile concentrates (30% of timed
  samples), but removing its bounds checks did not change that much, so that
  cost is the first dependent memory access of each command, not the checks.

## Can Java, Go and TypeScript reach 100M? @ 2026-10-28

Not shown to be impossible, but nothing tried gets close. Single core, W5 1k:
Rust 115M and C++ 105M (after forced inlining), Go 67.8M, Java 69M, TypeScript 34M.

- **Java (69M, needs +45%).** HotSpot cannot be made to inline like LLVM did
  (see above); the look-ahead removal, struct-of-arrays batch, JVM flags and an
  Unsafe map are exhausted or too small.
- **Go (67.8M, needs +48%).** After the hand-expanded fast path, in-place
  events and a fresh PGO profile Go is at 59% of Rust. The remaining cost is the
  core's code generation, not calls, sink dispatch or bounds checks.
- **TypeScript (34M, needs 3x).** V8 flags gave +8% (inlining budget); a
  struct-of-arrays batch was slower. No lever found within 2x of the target.
- Where they stand against Rust (single core): Java 60% and Go 59% on W5 1k,
  roughly 65-70% on the mixed W4; TypeScript about 30% on both. Nothing here
  predicts what further restructuring would gain, so no target is claimed.
