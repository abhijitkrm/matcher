## Ladder rescan fix @ 2026-10-09

W3 run for 1M ops instead of 100k (`vectorgen --workload w3 --n 1000000`)
cancels faster than it adds, so the book drains to a handful of orders.
Each time a side's last level emptied, the top-of-book rescan walked the
occupancy bitmap word by word to the end of the 1M-tick ladder (about
7,800 words) before returning "empty"; a profile put 98% of the time
there. Every port now keeps a summary bitmap (one bit per non-empty
bitmap word) and sets the cursor straight to empty when the side's count
reaches zero. Output is unchanged (golden vectors and bench checksums);
each port gained a randomized test of the cursor against a sorted set.

| impl | W3-drain before | W3-drain after | W3 (100k) / W2 / W4 |
|---|---|---|---|
| rust (8657dc7) | 0.60M | 13.0M | unchanged (A/B) |
| cpp (55091ea) | 0.64M | 15.3M | unchanged (A/B) |
| go (81542be) | 0.36M | 7.2M | unchanged (A/B) |
| java (20e563b) | ~1.2M | ~5M | unchanged (A/B) |
| ts (223341e) | 0.30M | 4.8M | unchanged (A/B) |

Apple M1, ops/s, single book. The default W3 (100k ops) never drained the
book, which is why the earlier tables did not show this.

- No workload collapses at 10M ops any more: before the ladder rescan fix,
  drained W3 ran at 0.3–1.2M ops/s.
- A deep book (1M live orders) costs roughly half the throughput in every
  port. The book no longer fits in cache, the same memory-bound curve as W5
  at smaller sizes.
- Max-column spikes of 100–330 ms are one-off pauses in long runs: GC in
  Go, TS and Java (W5's 334 ms), and first-touch page faults as W1 grows
  the C++, Go and TS pools to 10M orders.
- This sweep is what found matcher-ts's bench could not load a corpus over
  ~512 MB (V8's maximum string length); fixed in matcher-ts e7986ae.

## Reading it

- **C++ ≈ Rust** (within noise): 10–23M ops/s, p50 ≈ 41–42ns (measurement floor).
- **Go ~2–4× slower**: 2–9M ops/s — GC write barriers + `map` overhead; still
  respectable. GOGC variants not shown (default).
- **Depth curve (w5)** shows the expected memory-bound behavior: a 1k-order
  book is cache-resident (~20M ops/s); a 1M-order book spills to DRAM
  (~4M ops/s). This is the honest physics of order books — dense local books
  are fast; huge sparse books are memory-latency-bound.
- **Java** matches native-tier throughput once JIT-warm (12.5M ops/s on the
  sweep) but its max column shows occasional JIT/GC stalls — expected on a
  short unpinned run.
- **TypeScript (V8)** lands near Go's ballpark (~4–5.5M ops/s): per-command
  allocation in the harness and GC keep the tail heavier than the median.
- Max column reflects occasional page faults / TLB misses / scheduler noise on
  an unpinned macOS process.

## Per-language notes

- **rust**: pool slab + intrusive levels + bitmap ladder w/ top-of-book cursor
  + open-addr map (xor-fold hashing). All allocation at construction.
- **go**: same structures; `map[uint64]uint32` for ids (Swiss-table maps since
  Go 1.24 are genuinely good); sorted-slice tree index. GC pauses visible in
  p99.9+ columns.
- **cpp**: same structures; `std::map` tree fallback; template-dispatched sink
  (zero-overhead).
- **ts**: same structures on flat typed arrays (`Float64Array`/`Int32Array`
  pools, 32-bit bitmap words); sorted-keys `Map` tree fallback.
- **java**: same structures on flat `long[]`/`int[]` pools; `TreeMap` fallback;
  `@FunctionalInterface` sink. Numbers are JIT-warm.

## cpp chunk layout + apply_batch @ 2026-10-27

matcher-cpp Unreleased (inline 128-byte level chunks, tagged `OrderMap`,
`apply_batch`) against v0.2.0 (e4806a4), same machine, same corpora from
`bench/`, best of 3 reps, ops/s. "v0.2.0" and "latency" are the same
protocol (one timed `apply()` per command); "throughput" is the new
`apply_batch` mode, untimed per op. Not comparable with the other ports'
rows: those have no batch path.

| workload | v0.2.0 | new, latency | new, throughput | throughput + PGO |
|---|---|---|---|---|
| W1 build 1M | 14.1M | 19.1M | 37.2M | 37.4M |
| W2 sweep | 16.7M | 19.4M | 25.5M | 25.5M |
| W3 churn | 16.0M | 15.8M | 23.0M | 22.4M |
| W4 mixed | 14.6M | 14.7M | 39.7M | 39.9M |
| W5 1k live | 25.5M | 25.7M | **91.5M** | 89.9M |
| W5 100k live | 11.9M | 15.2M | 23.2M | 23.4M |
| W5 1M live | 4.5M | 5.3M | 13.1M | 13.1M |

- The 80–90M ops/s figure is W5 at 1k live orders in throughput mode, where
  the whole book is cache-resident. It does not hold for larger books:
  23M at 100k live and 13M at 1M live.
- In latency mode the layout alone helps W1 (+35%), W5 100k (+27%) and
  W5 1M (+19%); W3 and W4 are flat. Most of the headline gain comes from
  batching, which also removes the ~40 ns per-op timer.
- PGO (clang `-fprofile-instr-use`, trained on all workloads) is within
  noise on every workload; left optional, off by default.
- Correctness: golden suite (including `apply_batch` vs `apply`), ladder,
  regress and snapshot tests pass under ASan+UBSan; `diffuzz.sh` with
  `SAN=1` is 5-way identical on seeds 1-8 (20k commands each).

## rust chunk layout + apply_batch, and aggregate (shard-per-core) @ 2026-10-27

matcher-rust (Unreleased: LAYOUT.md chunk store, tagged `OrderMap`,
`apply_batch`) on the same machine and corpora as the cpp section above.
Apple M1, 4 P + 4 E cores, best of 5 reps, ops/s. Single-core rows use
`--mode throughput`; aggregate rows use `--mode scale` (BENCH.md §2.1:
8 threads, each with its own book and symbol partition, no shared state;
total = 8 × ops / slowest thread). Rust numbers are for
`--features prefetch` with `-C target-cpu=native`; the default build
(no `unsafe`, no prefetch) differs only on W4 (23.6M) and W5 1M (9.4M).

| workload | rust, 1 core | rust, 8 shards | cpp, 1 core | cpp, 8 shards |
|---|---|---|---|---|
| W1 build 1M | 37.7M | 56.2M | 37.2M | 63.4M |
| W2 sweep | 27.9M | 78.8M | 25.5M | 78.1M |
| W3 churn | 23.2M | 65.7M | 23.0M | 68.4M |
| W4 mixed | 40.5M | **109.8M** | 39.7M | **112.5M** |
| W5 1k live | **94.0M** | 284.2M | **91.5M** | 304.5M |
| W5 100k live | 24.6M | 75.3M | 23.2M | 68.2M |
| W5 1M live | 13.3M | 39.2M | 13.1M | 40.1M |

- **Single-core and aggregate are different claims.** Single-core is the
  engine's speed on one book. Aggregate is what a shard-per-core
  deployment sustains; it is not 8× because the 4 E-cores are slower
  and the shared L2/memory bandwidth saturates (W5 1M: 13M per core
  alone, 4.6M per thread at 8 threads).
- The realistic mixed workload (W4) crosses 100M ops/s only as an
  aggregate: 110M (rust) and 112M (cpp) on 8 shards. On one core it is
  40M, limited by cache misses on a 100k-order book, not by the code.
- Single-core above 100M was not reached: the best case (W5 1k live,
  everything cache-resident) is 94M. Always-on prefetch for books under
  64k live orders was tried and is far worse (62M), so the threshold in
  LAYOUT.md §4 stays.
- Noise: the machine runs other apps; individual runs of W5 1k vary
  87–95M. Compare builds with interleaved A/B rounds, not single runs.

## java chunk layout + applyBatch + aggregate @ 2026-10-28

matcher-java (Unreleased: LAYOUT.md chunk store on flat `long[]`, tagged
`OrderMap`, `applyBatch`) on the same machine and corpora. JDK 20, Apple M1,
`-Xms2g -Xmx4g -XX:+UseParallelGC` (`-Xms4g -Xmx8g` for scale), best of 15
reps (JIT-warm), ops/s. Throughput = `--mode throughput`; 8 shards =
`--mode scale`.

| workload | java, 1 core | java, 8 shards | rust, 1 core | cpp, 1 core |
|---|---|---|---|---|
| W1 build 1M | 27.5M | 47.4M | 37.7M | 37.2M |
| W2 sweep | 24.0M | 78.7M | 27.9M | 25.5M |
| W3 churn | 18.5M | 32.8M | 23.2M | 23.0M |
| W4 mixed | 29.4M | 57.5M | 40.5M | 39.7M |
| W5 1k live | 69.1M | 250.0M | 94.0M | 91.5M |
| W5 100k live | 19.1M | 41.2M | 24.6M | 23.2M |
| W5 1M live | 6.2M | 21.4M | 13.3M | 13.1M |

- **The look-ahead pipeline is off by default in Java** (LAYOUT.md §4 allows
  skipping it). Java has no non-blocking prefetch, so the pipeline's plain
  loads stall retirement. With it on, W4 ran at 12.8M and with it off at
  27.9M (2.2x); W3 +62%, W5 100k +54%, W5 1M +6%.
  `setPrefetchThreshold(n)` re-enables it; the golden suite forces it on.
- **`CommandBatch`**: a struct-of-arrays batch (`applyBatch(CommandBatch, …)`)
  with a byte opcode instead of `Command` objects and `instanceof` dispatch.
  Same events (golden suite checks it against `apply` for every vector);
  +3-7% over the `Command[]` path. The bench uses it unless `-Dbatch=obj`.
- ParallelGC over the default G1: +17% on W4 (12.9M → 15.1M, before the
  two changes above; cause not investigated). `-XX:-TieredCompilation`, raised inline limits and
  `LoopUnrollLimit=0` were all neutral or worse.
- Java reaches about 72-74% of native single-core on W4 and W5 1k. The
  rest is bounds checks and no prefetch; no single hot spot was found.
- Correctness: golden suite (including `applyBatch` and `CommandBatch` vs
  `apply`), snapshot and ladder tests pass; `diffuzz.sh` is 5-way identical
  on seeds 1-8.

## go chunk layout + ApplyBatch + aggregate @ 2026-10-28

matcher-go (Unreleased: LAYOUT.md chunk store, tagged `omap`, `ApplyBatch`,
PGO profile for `matcherbench`) on the same machine and corpora. Go 1.27,
Apple M1, best of 15 reps, ops/s. Throughput = `--mode throughput`; 8 shards
= `--mode scale`.

| workload | go, 1 core | go, 8 shards | java, 1 core | rust, 1 core |
|---|---|---|---|---|
| W1 build 1M | 28.7M | 49.4M | 27.5M | 37.7M |
| W2 sweep | 22.9M | 77.1M | 24.0M | 27.9M |
| W3 churn | 18.6M | 39.8M | 18.5M | 23.2M |
| W4 mixed | 26.0M | 61.1M | 29.4M | 40.5M |
| W5 1k live | 60.9M | 222.7M | 69.1M | 94.0M |
| W5 100k live | 17.5M | 41.1M | 19.1M | 24.6M |
| W5 1M live | 7.9M | 26.1M | 6.2M | 13.3M |

- **Look-ahead threshold raised from 64k to 256k live orders in Go.** Go has
  no prefetch intrinsic either, so the pipeline's plain loads cost on books
  that still mostly hit L2. A/B on W4 (about 100k live): 19.0M with the
  pipeline, 26.7M without. On the 1M-order book it wins: 7.9M vs 6.1M.
  Thresholds 2^17-2^19 all keep both results; 2^18 is used. The pipeline is
  on only for the dMap + dChunk stages. `-tags matcher_noprefetch` turns it
  off for comparison. (This lifted W2 as well, 18.9M → 22.9M.)
- **PGO**: `cmd/matcherbench/default.pgo` is worth about +7% (W5 1k 56.7M →
  60.8M). It lets the compiler inline the `priceIndex` wrappers and ladder
  calls at hot sites; without PGO they exceed the inliner's budget of 80
  (cost 117-129). A profile regenerated from the new code was no better.
- Bounds-check elimination (`-gcflags=-B`) and `GOGC=off` changed nothing,
  so neither bounds checks nor the GC is the limit.
- Go is at about 65% of Rust on a cache-resident book (W5 1k) and 59% on
  the 1M-order book; the rest is codegen (register allocation, no
  non-blocking prefetch). Not chased further.
- Correctness: golden vectors, `ApplyBatch` vs `Apply` on a 300k-order book
  (the test fails if the pipeline is not engaged), snapshot and ladder
  tests pass; `diffuzz.sh` is 5-way identical on seeds 1-8.
